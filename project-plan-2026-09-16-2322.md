## Goal

Today's nested HL/LL trainer builds **two independent** prompt dataloaders, each sized so one phase alone walks the dataset once over its `num_iters`. That makes `num_iters≈79` the only way to get ~128-prompt batches, which inflates `total_training_steps = N_HL×(N_LL+1)` to thousands and makes "epoch" meaningless across phases. This Goal adds a config-gated **shared prompt stream**: LL and HL pull consecutive batches from one dataloader; one epoch is `N_HL×(N_LL+1)` on-policy updates (default N=8 → 72 steps, batch ≈136 for D=10000/ws=8); train for `E=4` epochs (288 steps); `save_freq`/`test_freq` count `global_steps`. Legacy path stays when the flag is off. New mode becomes the default in all launch profiles.

### S2 — Shared prompt stream + epoch loop (trainer/workers/Hydra defaults)

**Goal:** Implement the feature behind `phases.shared_prompt_stream` so shared mode uses one dataloader, an outer epoch loop, step-based save/test, and epoch-scaled scheduler horizons — without breaking the legacy path.

**Why the code looks this way:** Two phase dataloaders with independent samplers were chosen so each phase could “see the dataset once” over its own `num_iters`. That couples batch size to a large `num_iters` and makes HL/LL consume disjoint reorderings. Shared stream keeps on-policy freshness (new gen every update) but makes consecutive LL/HL steps advance one cursor so `steps_per_epoch` ≈ one dataset pass.

**Read first:**

- `ECHO/training/echo_ray_trainer.py`: `_PhaseDataloaders` (50–61), `_create_dataloader` (301–371), `_next_batch_dict` (373–383), save/test block in `_run_phase_iteration` (655–697), `fit` resume + loop (752–767)
- `ECHO/training/echo_fsdp_workers.py`: phase optimizer horizon (~154–167)
- `ECHO/training/config/echo_trainer.yaml`: `phases:` and `trainer:` blocks

**Do:**

1. In `echo_trainer.yaml`: add `phases.shared_prompt_stream: true` and `trainer.total_epochs: 4` (comment that epochs apply only when shared).
2. `_create_dataloader`:
   - If shared: `steps_per_epoch = N_HL * (N_LL + 1)`; `batch = (D // steps_per_epoch) // ws * ws`; build **one** `StatefulDataLoader`; expose it so both phases' `_next_batch_dict` advance the same iterator; keep `self.train_dataloader.state_dict()` / `load_state_dict` working for resume (thin wrapper OK — e.g. both phase keys point at the same loader, or a single-key wrapper compatible with checkpoint restore).
   - Else: keep existing per-phase loop unchanged.
   - `total_training_steps = E * N_HL * (N_LL + 1)` when shared (`E = trainer.total_epochs`); else current `N_HL * (N_LL + 1)`.
3. `fit`: when shared, outer `for epoch in range(E)` (resume: map `global_steps` → `(epoch, hl_cycle)` via `steps_per_epoch` and `cycle_len = N_LL+1`); log `training/epoch`. Legacy: keep single-pass cycle loop.
4. Save/test gating: shared → fire when `end_of_cycle` **and** `(global_steps % save_freq == 0)` (same for `test_freq`), still only on cycle-closing HL. Legacy → keep `(hl_cycle + 1) % freq == 0`.
5. `echo_fsdp_workers.py`: when shared, HL horizon `E*N_HL`, LL horizon `E*N_HL*N_LL`; else unchanged.

## Locked decisions

1. **Shared stream default on** in Hydra and all launch profiles; legacy remains via `shared_prompt_stream: false`.
2. **Schedule:** N_HL = N_LL = 8, E = 4 → 288 global steps; save/test_freq = 72 (one shared epoch in steps).
3. **Batch formula (shared):** `(D // (N_HL*(N_LL+1))) // world_size * world_size` with `drop_last=True` → 136 for D=10000, ws=8.
4. **Save/test (shared):** gated on `global_steps % freq == 0`, still only on cycle-closing HL (`end_of_cycle`).
5. **Save/test (legacy):** unchanged `(hl_cycle + 1) % freq == 0`.
6. **Group size** stays 16 in launch profiles.
7. **On-policy:** fresh generation every update (no replay of old rollouts across steps).
8. **Out of scope:** reward/advantage changes; killing current GPU runs; subsampling parquet; agent-submitted jobs.
9. **Operator note (not code):** ~288 × 12–14 min/step ≈ 2.5–3 days; use `save_freq=72` + `resume_mode=auto` across 2-day Slurm allocations.
